WebView Error & Crash Test Lab — Development Only

⚠️ Development testing only. Some tests may freeze or crash the WebView. Every test is manual — nothing runs automatically.

Configuration

Network tests (HTTP 404 / 500 / timeout) use a configurable base endpoint. The default is a public status-code echo service. Change it to your own backend if you want to test against it.

Expected paths: /404 → HTTP 404, /500 → HTTP 500, /200?sleep=30000 → slow response (for timeout). Default httpstat.us sends permissive CORS headers.

12 · Renderer Crash / Process Gone  ⚠️ Renderer Crash Tests

A normal web page cannot reliably force an Android/iOS WebView renderer process to crash in a portable, safe way. This test does not guarantee a crash — it creates realistic renderer pressure by combining memory, DOM, canvas, WebGL and CPU load. Flutter's onRenderProcessGone only fires if the underlying renderer process actually terminates, which is platform- and device-dependent.
RENDERER-001idle

Sequentially: allocate memory → build large DOM → create big canvases → stress WebGL → CPU burst. Keeps references alive.

Flutter InAppWebView Events To Monitor

  • onConsoleMessage
  • onLoadError
  • onLoadHttpError
  • onReceivedError
  • onReceivedHttpError
  • onRenderProcessGone
  • onWebViewCreated
  • onLoadStart
  • onLoadStop
JavaScript errors and console.error messages do not necessarily trigger Flutter WebView load-error callbacks. They surface through onConsoleMessage. Renderer crashes / process termination are a different class of event (onRenderProcessGone).

Expected pipeline:
Web Test → JS error / console.error / WebView failure → Flutter InAppWebView → onConsoleMessage / onRenderProcessGone / error callbacks → Flutter logging → Firebase Crashlytics

Firebase is intentionally not included here — the Flutter app owns Crashlytics. This page only generates browser/WebView errors. Correlate using the [TEST: ID] markers in each log line.
